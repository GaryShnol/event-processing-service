# AI usage

## Tools

- An earlier AI chat produced my first design summary (rows 1 and 2).
- Claude (chat and voice in the desktop app), to review that summary, argue through the trade-offs and draft `ARCHITECTURE.md` and `CLAUDE.md`. It made the first two commits, cleaned up the project skeleton and wrote the MIT license text. Later it talked through each review finding with me, and in phases 2 and 3 it ran the live API checks against my running stack through the app's browser.
- Claude Code, for all the code, tests and documentation from phase 1 onward, working from `CLAUDE.md`, and for the review agents it started.

## How I worked with it

I fixed the design before any code was written. Claude drafted `ARCHITECTURE.md` and `CLAUDE.md` in chat. I didn't rewrite them by hand: I reviewed each draft, questioned the parts I disagreed with and made the decisions, and Claude applied the changes. Where I changed the direction: during design, one compound customer index instead of two (row 4) and SQS instead of the Kafka I wanted (row 5); in phase 1, local AWS credentials out of the application config (row 10) and a startup check instead of a note (row 11).

I generated the project skeleton on start.spring.io, and Claude in chat cleaned it up and committed it. I committed the LICENSE file Claude wrote. From phase 1 onward Claude Code wrote every file; I edited none by hand. `CLAUDE.md` gives it the code rules and five phases, each on its own branch with criteria that can be checked. For each phase it built the code in small commits, checked the criteria and started a separate agent, which hadn't written the code, to review the diff as a strict senior engineer. I read every finding of that review in full, decided each one with Claude in chat, and told Claude Code what to fix, defer or keep. Then I pushed the branch, opened the PR and merged it. I kept the push and the merge for myself on purpose.

## How I verified the output

The main evidence is the tests, because they run the guarantees against real MongoDB and ElasticMQ in Testcontainers rather than mocks: 20 concurrent `POST`s with one `eventId` store one document and publish once, concurrent claims have exactly one winner, a stale `claimToken` can't complete, the same message delivered twice runs the processor once, and the recovery tests drive a transient failure, an exhausted event, a lost message, a failed publish and an unparseable message to their end state. Claude Code also broke the code on purpose to check that some of these tests fail (rows 12 and 15).

What I checked myself:

- I ran `mvnw verify` myself in phases 1 and 2.
- In phase 1 I ran `docker compose up` and checked the health endpoint, both queues and their settings, and that the app runs as a non-root user. In phase 4 I stopped ElasticMQ, posted an event and got `202`, started ElasticMQ again and saw the sweeper bring the event to `PROCESSED`.
- In phases 2 and 3 I read the results of the live API calls Claude in chat ran against my stack (`POST`, duplicates, the 409, validation errors, `GET`, the customer query, `PROCESSED` and `FAILED`).
- After each phase I checked the `git diff` of `CLAUDE.md`, so I would have seen any change Claude Code made to its own rules.
- I read every review-agent finding in full, and looked through each PR's changed files before merging. I didn't review every diff line by line.

In phase 5 Claude Code ran the clean-clone check (a fresh clone, Docker build without cache, every README command, `mvnw.cmd verify`) and a fresh agent reviewed the three documents against the code and the assignment.

## Accepted, rejected and corrected AI suggestions

| # | What the AI suggested | What happened | Why |
| --- | --- | --- | --- |
| 1 | The design summary from an earlier AI chat listed "MongoDB (Mongoose)" | Caught by Claude when I asked it for honest feedback on the summary; rejected | Mongoose is a Node.js library. The stack is Java, so Spring Data MongoDB |
| 2 | That same summary treated a DLQ redrive policy as the whole failure strategy | Claude pointed out the gap in its first review of the summary; extended | A message moved to the DLQ leaves the event stuck in `PROCESSING`, so `GET` would show the wrong status. Now MongoDB decides when an event is `FAILED`, and a sweeper handles stuck events |
| 3 | Claude pointed out that my plan of Mockito-only tests couldn't prove the concurrency guarantees | Accepted | A mock can't show that a unique index or `findAndModify` prevents a race. The concurrency tests run on real MongoDB |
| 4 | Claude's plan used four indexes, two of them for the customer query | I pushed back | I asked why not a single index on customer, status and timestamp. That order would have broken range and sort when no status is sent, but the question led to one index ordered `customerId, occurredAt, _id, status` that covers both cases. Two indexes became one |
| 5 | Claude argued for keeping SQS when I wanted Kafka | Accepted | The assignment asks for SQS explicitly, and for a work queue SQS fits better. Kafka on MSK is documented as the path if consumers ever need replay |
| 6 | Claude's plan used LocalStack for local SQS | Claude found the problem itself while writing the docs; replaced with ElasticMQ | The current LocalStack image needs an account and auth token since March 2026, so `docker compose up` would fail for a reviewer |
| 7 | Claude recommended Spring Boot 3.5 as the safer choice, in a voice conversation | Claude corrected itself while consolidating the decisions | Spring Boot 3.5 reached end of open-source support in June 2026, so I chose Spring Boot 4.x |
| 8 | Claude's first plan was about 8 hours, including custom metrics | Cut | The assignment estimates 4 to 6 hours. I kept logs with `eventId` and health checks, and listed the metrics as production work |
| 9 | Claude's `CLAUDE.md` draft asked for "the Spring Cloud AWS 4.1.x release documented as compatible with" Spring Boot 4.1 | Claude Code found it in phase 1 and reported it | No release documents Boot 4.1: the compatibility table lists 4.x with Boot 4.0.x, and 4.1.1 is built against Boot 4.0.8. I decided to stay on Boot 4.1.3 with 4.1.1, the latest 4.1.x, on the condition that phase 3 proved send and receive. On Boot 4.1.3, phase 1 tests show the SQS client reaches the queues, and phase 3 tests send with `SqsTemplate` and receive with `@SqsListener` with Jackson 3 converting the body both ways, so I didn't need the Boot 4.0.x fallback. It needs no Jackson 2 bridge |
| 10 | Claude Code's phase 1 config put local AWS credentials and a localhost SQS endpoint in `application.yaml` as defaults | Caught by the review agent; I had them moved out | Static credentials override the default chain, so in AWS they would have replaced the ECS task IAM role. The base config now sets none; compose, the Testcontainers config and `.env.example` supply the local values |
| 11 | After review, Claude Code documented the timing rules (lease below the visibility timeout, `maxAttempts` below `maxReceiveCount`) as a note in `.env.example` | I chose a startup check instead | A note doesn't stop a wrong value. The app now reads the queue's visibility timeout and redrive policy at startup and refuses to start if either rule is broken |
| 12 | Claude Code's phase 2 explain tests built their own sort document instead of using the repository's query | Caught by the review agent, fixed | Changing the repository's sort would have left the "no in-memory SORT" tests green. They now explain the exact query the repository sends, and Claude Code checked that they fail when the sort is broken |
| 13 | Claude Code hashed the request timestamp at full precision but stored it in MongoDB at millisecond precision | Caught by the review agent, fixed | The stored document disagreed with its own hash and `GET` returned a different `timestamp` from the one sent. The timestamp is now truncated to milliseconds before hashing and storing |
| 14 | Claude Code's phase 3 logged a permanent failure as "Event failed: <reason>", and the reason quotes the amount | Caught by the review agent, fixed | The amount is a payload field and the rules say never log payloads. The log line now says only that the event failed; the reason stays on the document and in `GET` |
| 15 | In phase 3, Claude Code committed `66636e5` while `./mvnw verify` was red | Caught by Claude Code, process changed | To check that the concurrency test can fail, it broke `claim` and then restored the file from a copy. The copy kept its old timestamp, so Maven's incremental build reused the broken compiled class. Its commit step only checked that the script ran, not Maven's exit code. The committed code was correct, and a clean `verify` on that commit was green. Since then it runs `clean verify` before every commit, and a failed build stops the commit |
| 16 | Claude Code's phase 4 error handler passed the cause to SLF4J as the last argument, and its test matched the message with a loose pattern | Caught by Claude Code when reading the log, fixed | SLF4J treated the cause as the throwable, so the line read "redelivered: {}" and repeated the stack trace the framework already logs. The handler now logs the cause as text, and the test asserts the exact message |
| 17 | Claude Code's phase 4 docs said every run logs the sweeper counts and that `eventId` is on every line the service writes; its `markRepublished` could write to a finished event | Caught by the review agent, fixed | A run that hits a publish failure logs no summary, the sweeper's bulk move to `FAILED` is logged as a count, not per event, and the scheduler's error line has no `eventId`. The docs now say so, and `markRepublished` matches only `RECEIVED` or `PROCESSING` |
| 18 | Claude Code's code from phases 1 to 4 had no operation timeout on MongoDB or SQS, a phase 4 test that passed even when a failed message was acknowledged, and a package cycle between `application` and `messaging` | Caught by a review of `main` after phase 5: seven Claude Code agents, each on one area, and a verifier that tried to disprove every finding; fixed | A MongoDB that stops answering blocked threads forever and a silent SQS held every `POST` for about 2 minutes. Every MongoDB operation now times out after 10 s with a `503`, and the publish after 3 s with a `202`, bounded on the send only so the listener's long polls are unaffected. The review's suggested one-line MongoDB fix would have turned the documented `503` into a `500`, because Spring Data doesn't classify the new timeout as a resource failure; the new test showed it, and the handler now maps it. The test passed because the sweeper re-published the stuck event; it now asserts a single publish, and fails when the error handler swallows the exception or acknowledgement is set to `ALWAYS`. `EventPublisher` moved into `application`. The same review led to `400` for out-of-range timestamps and huge page numbers, removing the unused `EVENTS_DLQ`, and the doc fixes |
